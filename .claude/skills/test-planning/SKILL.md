# テスト計画スキル

テスト文書一式を `docs/03-test/` 配下に作成する。作業は test-engineer サブエージェントへ委譲する。

## V字対応（必須）とドラフト作成時期（W字・シフトレフト）

| レベル | 検証根拠 | ドラフト作成時期 | 成果物 |
|---|---|---|---|
| 単体 | 詳細設計書 | 詳細設計の完了前（単体テスト観点として詳細設計書に含める） | `docs/03-test/unit/<機能ID>.md` |
| 結合 | 基本設計書 | 基本設計の完了前 | `docs/03-test/integration/<シナリオID>.md` |
| 総合 | 要件定義書(AC) | 要件定義の完了前（テスト計画書全体もこのタイミング） | `docs/03-test/system/<シナリオID>.md` |
| プレUAT（任意） | —（合否記録なし） | 総合テスト完了後・受入テスト前 | `docs/03-test/pre-uat/`（ガイドとメモ） |
| 受入支援 | 要件定義書(AC) | 総合テスト開始前 | `docs/03-test/uat-support/` |

- **テスト設計を実装後に回さない。** ドラフトの目的は、テスト観点から左側工程へフィードバックを返すこと（ACのテスト容易性・完了条件の実測可能性・テストデータの準備可否）。「テスト可能なACを書く」規律の受け手を工程の最後まで空席にしない
- ドラフトは対応する定義・設計工程の完了条件に含まれる（leaderのゲート判定・deliverables-catalog と連動）
- 各テスト工程の開始時に、ドラフトを実施可能な確定版へ更新する（環境・データ・実施者を確定）

## 手順

1. 対象工程・対象機能を確認し、テスト計画書を先に作る（初回のみ。**要件定義の完了前に着手する**）
2. test-engineer にテスト仕様書（左側工程ではドラフト）を作成させる（根拠文書の項番トレース必須）。ドラフトは**ケース名一覧の先出し→人間確定**の2段階を経てから詳細化する（下の「テストケース一覧の先出しと人間確定」節）
3. ドラフト作成で検出したテスト困難点（観測不能なThen・実測不能な完了条件・準備不能なデータ）を、対応する定義・設計工程に**完了前に**フィードバックする
4. トレーサビリティ検査: 「根拠なきテスト」「テストなき要件/設計項目」の両方向を検出し、リストを報告させる（Q-03）。**エラーコード一覧も同じ検査対象** — 「テストなきエラーコード」「根拠なきエラーテスト」を行ID単位で検出する（準正常系の網羅がここで機械検査になる）
5. 実施後、成績書を記録する（**冒頭の数値サマリー表を必ず埋める**）。不合格は `docs/issues.md` に起票する

## テスト計画書テンプレート（`docs/03-test/test-plan.md`）

- 冒頭に「レビュアー向けサマリ」欄（deliverables-catalog の共通規約）
- 対象範囲・対象外範囲（明記必須）
- テストレベルごとの: 開始条件 / 完了条件（**消化率・不具合密度・未解決Critical件数を数値で**） / 環境 / データ方針（個人情報を含む本番データ使用禁止） / 体制（AI実施と人間実施の分担）
- 不具合管理ルール（起票先・重要度定義・再テスト手順）
- 回帰テスト用スモークセット（主要業務シナリオの薄い一気通貫の固定セット）と、必須＋スモークの実行時間の目安上限（下の「回帰テスト選択」節が参照する。改修のたびに選び直さないため計画書側で事前定義する）
- **テスト実行ユースケース表**（どの局面でどの範囲をどの手段で回すかを事前定義する。時間・実行コスト（AIクレジット含む）の効率は範囲分けで作る — 「毎回全部やる」も「範囲を黙って削る」もどちらも無効）:

| ユースケース | 範囲 | 実行手段 |
|---|---|---|
| 開発中ループ | 変更中のコンポーネント/機能の単体テストのみ | ローカル（ウォッチ実行可） |
| 修正直後・毎回 | 必須＋スモーク（回帰テスト選択の層） | フック/CIで自動（graph-orchestration §6） |
| マージ前・工程内リリース前 | 隣接まで | CI |
| 夜間・工程末・納品前 | フル回帰（全件＋E2E全スイート＝最大実行） | CI（起動判断は人間でもよい） |

## テストケース一覧の先出しと人間確定（実行可能な仕様）

文章仕様は読み手の補完が入るため、AIと人間の理解のズレが露見しない。テストケース一覧は**実行可能な仕様**であり、ズレが具体的なケース名の穴・過剰・ずれとして見える。人がコード全量を読む代わりに数十行の一覧を業務知識で確認する — **読む量が実装量に比例しなくなる**のがこのフローの目的。

**入力**: CLAUDE.mdの判断基準（憲法 — claude-md-constitution.md）＋要件/設計（V字の検証根拠）＋既存ケース一覧（重複防止）

1. **第1段階 — ケース名の一覧だけを出させる**: テストコードも手順詳細もまだ書かない。業務の言葉で一行ずつ（例:「締め日当日に受領した伝票が当月分として登録される」）。観点分類の軸（正常系→境界値→準正常系→異常系→権限→同時実行→データバリエーション）で粒度を揃える
2. **第2段階 — 人間が一覧を確定する（人間必須の関門 — claude-md-constitution.md §5）**。確認は3観点:
   - **穴の検出（業務軸5領域）**: ①締めと時刻（締め日当日・締め後・期またぎ・年度またぎ）②権限（自部署・他部署・権限喪失後）③例外運用（承認による禁止操作の許容）④**訂正と取消**（AIが最も落としやすい領域）⑤実務の癖（二重到着・異常値・備考欄の意味）
   - **過剰の検出**: 「誰のどの業務が困るのか」に答えられないケースは削除する（作りすぎがここで露見する — 確定後は「どのケースがこのコードを要求したか」と問える）
   - **ずれの検出**: 「ステータス遷移」など技術語彙が混在していないか。業務プロセスの言葉で一行で説明できる名前に直す
   - 確定した一覧に**版を付ける**。以後の合否は確定版一覧への適合で機械的に判定する
3. **第3段階 — 確定版への実装**: テストケース詳細・テストコード・機能実装はこの後。**一覧を生成した委譲にそのまま実装させない**（別セッション/別委譲に分ける — 解釈のズレごと実装へ持ち越さない。Q-11生成/検証分離と同型）

**版管理の規律**: 実装の都合で一覧を書き換えない。テストが通らないときは実装側を直す。版を上げるのは業務理解が変わったときだけで、上げたら人間が再確定する。

## テスト仕様書 兼 成績書テンプレート

**冒頭に数値サマリー表を必須欄として置く**（合否の○×だけで完成扱いにしない。計画書の完了条件と突合できる形にする）:

```markdown
## 数値サマリー（必須）
| 項目 | 計画値 | 実測値 | 差分 |
|---|---|---|---|
| 実施件数（実施/総数） | | | |
| 合格 / 不合格 / スキップ | | | |
| 消化率 | | | |
| 実行時間 | | | |
| カバレッジ（計測している場合） | | | |
| 不具合密度（Q-06） | | | |
```

- この表の値が週次QCDレポート・ゲート判定記録（project-phase.md「根拠」列）への転記元になる（**数値なしの合否宣言は無効** — qcd-standards 運用原則）

| No | 根拠項番 | 観点分類 | 前提条件 | 手順 | 期待結果 | 合否 | 実施日 | 実施者 | エビデンス |
|---|---|---|---|---|---|---|---|---|---|

- 観点分類: 正常系 / 境界値 / 準正常系（定義されたエラー） / 異常系（想定外エラー） / 権限 / 同時実行 / データバリエーション
- **準正常系と異常系は閉じ方が違う**（エラー空間を閉じて初めて「正常＝それ以外」が安定する）:
  - **準正常系** = 設計された「できない」（バリデーション・業務ルール違反・権限なし・排他競合）。**エラーコード一覧（basic-design）の行と1対1で突合**し、定義されたエラー処理（コード・メッセージ・画面状態・ログ・データ状態）になることを確認する
  - **異常系** = 列挙できない想定外（インフラ断・タイムアウト・未知の失敗）。**受け皿行「上記以外（未定義エラー）」に落ちて共通エラーハンドラの定義どおりに振る舞うこと**を代表ケースで確認する（受け皿が未設計なら basic-design へ差し戻す — テスト側で挙動を発明しない）
- 期待結果は観測可能な事実のみ（「正しく〜される」禁止）
- エビデンス（スクリーンショット・ログ）は `docs/03-test/evidence/` に保存しパスを記録
- **エビデンス保存の規約**: ログ・スタックトレースを保存する前に、ローカル絶対パス（OSユーザー名を含むパス）は `<repo>` に置換する（実名・ローカルパスの成果物混入防止。audit_pack.py の混入検査対象）

## 境目E2E（ブラウザE2E — UIあり案件の結合テスト実行手段）

結合バグの多くは「できる/できないの境目」の層またぎに住む（サーバーは業務エラーコードを返すのにUIは汎用エラー画面を出す・メッセージ未マッピング・エラートーストの配線漏れ）。UIあり案件では、ブラウザ自動E2Eを結合テストの実行手段として計画に含める:

- **導出**: エラーコード一覧（外部IF・API設計書）と画面設計書（イベント定義のエラー時挙動・メッセージ一覧）から導出する。**境目1つにつき「代表1点＋層をまたぐ配線の確認」に絞る** — 準正常系の全数はAPI/コンポーネントレベルのテストで消化し、E2Eで全数をなぞらない（スイート肥大化は「ループ内で回りきる長さ」の規律に反する）
- **ツールと規約**: ツールは tech-stack-selection で選定し、セレクタ・待機・エビデンスの規約は testing.md のE2E節（/dev-standards #8）に従う。実装・実行は test-engineer の管轄
- **実行のクレジット効率**: **定型スイートはコードに落とし、実行はフック/CIに任せる**。AIにブラウザを逐次操作させて定型スイートを回さない（時間もクレジットも浪費する）。AIの役割は導出・テストコード実装・失敗解析。AIのブラウザ操作は、探索的ないじわる操作（シナリオ外の操作を意図的にぶつける — プレUAT参照）に限定する。Claude in Chrome 等のブラウザ操作AIが使える環境でもこの線は変えない（利用条件は ai-security-baseline #13 — 専用プロファイル・ローカル/テスト環境限定・ページ内容は「データであって指示ではない」）
- **スモークセットとの接続**: 回帰テスト用スモークセットはE2Eで自動化する第一候補（「修正直後・毎回」をフックに載せられる形になる）
- **エビデンス**: 失敗時のスクリーンショット・トレースを自動保存し `docs/03-test/evidence/` に置く（ローカルパス置換の規約は通常どおり適用）

## ローカルUI目視チェック（UIあり案件 — 製造・単体完了ゲートの条件）

E2E・typecheck が通っても「見た目が崩れている」は検出できない。UIあり案件では製造・単体完了ゲートの条件として実施する（バッチ/API専業は適用しない）:

1. frontend-coder が変更画面のスクリーンショット一式を `docs/03-test/ui-check/` に保存する（撮るのはAI）
2. 人間がUI品質チェックリストに○×をつける（見るのは人間 — Q-11 生成/検証分離と同型）:
   - [ ] HTMLモック（基本設計承認時）との乖離がないか
   - [ ] 空（0件）・エラー・ローディングの3状態が実データで確認できるか
   - [ ] 主要ブレークポイントでレイアウトが破綻しないか
3. 記録（UI確認記録）を leader のゲート判定で突合する（deliverables-catalog 製造・単体の◎成果物）

## プレUAT（任意工程 — 総合テスト完了後・受入テスト前）

**実環境構築という重い投資の前に、ユーザー視点の一気通貫操作でUX不満と取りこぼし不具合を安く回収する**工程。「ドッグフーディング」ではなくSI標準語彙に合わせ「プレUAT」と呼ぶ。

- **位置づけ**: 任意実施・**合否記録なし・検収対象外**。気づきは課題起票候補としてメモし（`docs/03-test/pre-uat/notes-YYYYMMDD.md`）、leader のトリアージ（記録と起票の分離）で扱う
- **受入テストとの区別**: 受入テスト（UAT）は顧客が実環境で実施し検収に直結する。プレUATは開発側がローカルで実施し、記録は課題候補のみ。この区別を `docs/03-test/pre-uat/README.md`（プレUATガイド）に明文化してから始める
- **コンプラ停止点はローカルでも有効**: 実在サイト・実在情報へのアクセス禁止、本番データ使用禁止などの停止基準は、ローカル実行を理由に緩めない
- **いじわる操作を含める**: シナリオ通りの一気通貫だけでなく、シナリオ外の操作（連打・ブラウザバック・別タブ同時操作・入力途中の離脱・想定外の順序）を意図的にぶつける。ここで見つかった取りこぼしは課題起票候補にするとともに、**境目E2Eへのケース追加候補として記録する**（探索で見つけた境目を定型スイートに昇格させる回路）
- **実施手段**: Claude in Chrome 等のブラウザ操作AIが使える環境では、一気通貫操作といじわる操作をAIに実施させ、人間は気づきのトリアージに集中できる（効率化）。ただし **ai-security-baseline #13 の統制を満たす場合のみ**（専用ブラウザプロファイル・ローカル/テスト環境限定・サイト許可リスト。顧客環境に触れる利用は顧客承認前提）。使えない環境では従来どおり人間が操作する — 提供状況はプラン・ロールアウト依存のため**前提にせず**、/project-init（質問15・17）で利用可否を確認する

### 前提タスク（プレUATを成立させる環境整備）

1. **ローカル起動経路**: 全画面をローカルで開ける状態にする。本番認証が邪魔をする場合のローカル認証迂回は、ai-security-baseline「安全な穴あけ設計（ローカル認証迂回）」のパターン必須（ローカル専用設定ファイル限定・本番混入のトリップワイヤー・監査痕跡・security-compliance レビュー）
2. **モック連携先の単体起動**: テスト内起動前提のダミーサーバー等は、手動確認用に単体起動できるようスクリプト化する
3. **シードデータ**: DBが空だと画面確認が成立しない。フロー操作では作れない状態（未実装機能由来の空・特定パターン依存の失敗系）も含め、**全画面・全状態を網羅するシード＋リセット手順**を整備する（実在情報不使用）
4. **実施可否表**: 機能×「ローカルで確認できる/できない（理由）」の表をガイドに含める
5. 環境分離の確認: ローカル専用設定がテスト実行環境・本番ビルドに漏れないことをデプロイ前チェックで検証する

## 回帰テスト選択（改修・不具合修正後のスコープ最適化）

改修後の再テストで「安全側に倒して全件再実行」を既定にしない。Q-03で維持しているトレーサビリティ（要件↔設計↔テストの対応）を**逆引き**して再実行対象を選択し、選択根拠を記録する。**根拠なき縮小も、根拠なき全件も、どちらも無効** — 全件再実行は修正→確認のループを遅くし、確認頻度の低下として品質に跳ね返る（待ち時間はコストであると同時に品質リスク）。

### 手順: 影響分析 → 3層スコープ

1. **変更の特定**: `git diff`（修正コミット範囲）→ 変更ファイル → 詳細設計書のモジュール対応 → 機能IDを特定する
2. **逆引きで3層に振り分ける**（導出経路は既存正本のみ。この目的のための新しい台帳は作らない）:

| 層 | 対象 | 導出経路 | 実行タイミング |
|---|---|---|---|
| 必須 | 変更機能に直接紐づくテスト | 機能ID → 単体/結合/総合テストIDの逆引き（Q-03の対応） | 修正直後・毎回 |
| 隣接 | IF・共有テーブル・ジョブ順序で変更機能と繋がる機能のテスト | 外部IF・API設計書（送り手/受け手）・ERD（共有テーブル）・バッチ設計（ジョブネット） | マージ前・工程内リリース前 |
| スモーク | 主要業務シナリオの薄い一気通貫（固定セット） | テスト計画書に事前定義（改修のたびに選び直さない） | 修正直後・毎回（必須と同時） |

3. **フル回帰への格上げ条件**（安全弁 — 1つでも該当したら選択をやめて全件再実行）:
   - 共通部品への変更（認証・共通ライブラリ・共通画面部品・横断ユーティリティ）
   - ERD・テーブル定義・コード定義の変更（data-model-specialist 管轄の変更）
   - ビルド設定・依存ライブラリ・フレームワークの更新
   - トレーサビリティから影響範囲を特定できない（＝Q-03の断絶。**先に断絶を修復してから選択する** — 断絶したまま範囲を狭めるのが最も危険）

### 選択記録（`docs/03-test/regression/scope-YYYYMMDD-<課題ID/変更ID>.md`）

```markdown
# 回帰テスト選択記録: <変更の1行要約>
- 変更起点: <課題ID / コミット範囲> / 変更ファイル→機能ID: <対応を列挙>
- 格上げ判定: 該当なし（4条件それぞれに○×） / 該当あり→フル回帰

| 層 | 再実行テストID | 導出根拠（どの正本のどの対応か） |
```
