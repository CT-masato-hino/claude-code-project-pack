# ワークフロー実行標準（並列オーケストレーション）

線形の逐次委譲（A→B→C）から、**依存のない仕事を同時に走らせる並列ワークフロー実行**（Claude Code 側の正式名は dynamic workflows: 決定的なオーケストレーションスクリプトで最大16並列・累計1000エージェントまでファンアウト）への接続標準。4層モデル（プロンプト→コンテキスト→ハーネス→ループ）の**ループ層の実行エンジン**にあたり、README 4層モデル表では「グラフ（実行）」層の実装として参照される（知識のグラフ＝事実と関係の外部化は別軸。README「知識のグラフ」節が正本の対応表）。

本パックの既存統制はそのままグラフの土台になる — Q-11（生成と検証の分離）＝検証ノードの独立性、品質ループの停止判断＝自己増殖・Goodhart検知、QCD基準の数値必須＝動かないアンカー、ERD独占管轄・採番前の台帳突合＝並列衝突の裁定。**この標準はそれらの「並列幅」への適用ルール**であり、新しい原則を発明しない。

## 1. 適用基準（グラフにしてよい仕事・してはいけない仕事）

エッジの判定が出発点: 「次の工程は前の工程の**出力を実際に読むか**」。読まないなら依存はなく、並列にできる。

**適用してよい**（3条件をすべて満たすもの）:
1. 相互に依存しない同型タスクの繰り返しである（1ファイル・1機能・1観点ごとに独立）
2. 各結果を機械的・独立に検証できる（テスト・grep・基準IDとの突合）
3. 結果のマージ方法と矛盾時の裁定者が事前に決まっている

**適用してはいけない**:
- 人間の判断ゲートそのもの（工程ゲート承認・リスク受容・検収・顧客提出）— **V字の人間ゲートは常にワークフローの外に置く**。グラフはゲートの「入力を揃える」までを担う
- 逐次依存が本質の工程（各ステップが前段の出力を読む設計作業など）— 並列化しても調整コストが増えるだけ
- 探索的作業（何を探しているかまだ分からない調査）— 舵を切れる単一エージェントの方が適する
- 小さく孤立したタスク（1バグ修正・1関数追加）— ワークフローは純粋なオーバーヘッド

## 2. 開始条件チェックリスト（enterprise-controls §B の並列版 — 1つでも欠けたら開始しない）

- [ ] **ハーネス完備**: deny設定（ai-security-baseline §2）・ブランチ保護が適用済み（ハーネスなしのファンアウトは事故を並列量産する）
- [ ] **作業場所の分離**: 各エージェントがどこで作業するか定義したか。ファイルを書き換えるタスクは worktree 分離を必須とする（同一ワークスペースでの並列書き込みは競合する — 読み取り専用タスクは分離不要）
- [ ] **マージ計画と裁定者**: 結果をどう統合するか・2つのエージェントの結論が矛盾したら誰が裁くか（leader / 該当ドメインの独占管轄者）を事前に決めたか。ID採番を伴うタスクは採番の衝突防止（main台帳突合）をワークフロー設計に含めたか
- [ ] **検証の独立性（Q-11の並列適用）**: 検証エージェントは実行エージェントと別か・**実行エージェントの文脈を引き継いでいないか**（同じ文脈を渡した検証は自己同意にすぎない）。検証は「完了したと言ったか」ではなく実測（テスト結果・grep結果・基準値）に対して行うか
- [ ] **件数上限つきの初回実行**: 全量の前に上限つき（目安: 20件）で1回走らせ、挙動と使用量を確認したか（ワークフローは通常セッションより使用量が大きい。調整コストの節約であって実行コストの節約ではない）
- [ ] **停止手段と上限**: 途中停止の方法・件数/コスト上限・失敗時のエスカレーション先が決まっているか
- [ ] **結果の正本化**: ワークフローの結果を docs/04-reports/agent/（エージェント報告書）と成果物台帳に残す設計か（チャット・スクリプト変数の中の結果は揮発する）

## 3. 標準レシピ（同じ形 — 実エッジの特定→ファンアウト→独立検証→統合 — の適用例）

### レシピ1: トレーサビリティ突合（leaderゲートの入力を揃える）
- ファンアウト: 画面・IF一覧の1項目ごとに突合エージェント（詳細設計記述/実装ルート/UI/テストの実在をgrep確認）
- 検証: 別エージェントが「欠落」判定のみ再確認（false positive の除去）
- 統合: 欠落一覧＋理由候補を1本のレポートにし、leader の実装工程完了判定（ゲート判定記録）の入力にする

### レシピ2: 逆生成（P2既存コード・P3モック案件の初動）
- ファンアウト: 機能単位で1エージェントずつ、機能一覧行＋ACドラフトを逆生成
- 検証: 別エージェントがテスト可能性（ThenがObservableか・異常系があるか）を検査。不能なACは差し戻し
- 統合: 未確定事項を Q-ID 起票（採番はワークフロー完了後にまとめて実施 — 並列採番の衝突防止）。成果は承認単位で分割して人間レビューへ（レビュアー向けサマリ規約）

### レシピ3: 納品前スイープ（/delivery-package の入力を揃える）
- ファンアウト: 観点別に並列（秘密情報・実名・ローカルパスの混入 / 規約準拠 / 仮定マーカー残存 / 版数・承認記録の欠落）
- 検証: 検出項目ごとに敵対的検証（「本当に問題か」を反証させ、多数決で残す）
- 統合: ギャップ表の形で /delivery-package の手順2へ。欠落を勝手に埋めない原則はそのまま

## 4. 運用

- **保存と再実行**: 有効だったワークフローは保存して名前で再実行できる。案件で定着したものはテーラリング記録に登録し、レシピの改変（対象・観点の差し替え）は同じ統制チェックリストを通す
- **定期実行との関係**: 定期・無人で回すループの統制は enterprise-controls §B が正本（本標準は「1回の実行の並列幅」の統制）。両方に該当する運用（定期×並列）は両方のチェックリストを満たす
- **プラン・環境差**: workflows の利用可否・既定設定はプランで異なる（/config で確認）。Bedrock/Vertex/Foundry 経由はクォータ（RPM/TPM）に当たりやすい — ai-security-baseline §0-2 の考慮点を先に確認する
- **適用しない判断も記録する**: 小規模・逐次依存の強い案件では「ワークフロー実行は適用しない」をテーラリング記録に残す（過剰装備の防止。削るのが正しい、の原則どおり）。パック側で検討のうえ採用していない機構と、その再検討条件は tailoring-guide §7 が正本

## 5. アンカー（グラフを正直に保つもの）

ノードを増やすだけでは真実は増えない。互いに承認し合うだけのエージェント網は、単一ループと同じ壊れ方を規模だけ大きくして再演する。グラフには「議論の余地がないノード」を必ず含める:

- 実際に実行されたテスト（「通るはず」ではなく通った実測 — 数値サマリー表）
- 実測に対する検証（qcd-standards「数値なしの合否宣言は無効」）
- エージェントが調整できない凍結ルール（deny設定・QCD基準値 — 変更はPRレビュー経由のみ。最適化器が真っ先に弱めたがるものほど凍結する）

**順序の注記（知識のグラフが先）**: 並列に走らせた結果を突き合わせる正本（知識のグラフ — 機能ID・Q-ID台帳・成果物台帳・引き継ぎコンテキスト。README「知識のグラフ」節）が無いままファンアウトすると、エージェントが互いの主張を承認し合うだけになる。本パックでは知識のグラフが先に存在したため、実行のグラフを後から安全に足せた。導入先で本標準だけを先に採る場合は、突合先の正本が揃っているかを開始条件チェックリストより前に確認する。
