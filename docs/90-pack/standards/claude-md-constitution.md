# CLAUDE.md憲法運用標準（判断基準の書き方と育て方）

仕様を完全に書き切ることは本質的に不可能であり、書き切ろうとするとボトルネックが実装→レビュー→仕様合意へ移動するだけで消えない。本標準は「何を書き切るか」ではなく「**不完全なまま、空白の埋め方を制御する**」ためのルール。CLAUDE.md を個別指示の置き場（指示書）ではなく、書かれていない場面でAIが演繹に使う**判断基準の正本（憲法）**として運用する。

原則: **細かい規則を網羅せず、原則を与えて個別の判断はモデルに演繹させる。**

## 1. 指示と判断基準の違い

| 指示として書いた場合 | 判断基準として書いた場合 |
|---|---|
| 「この画面の確定ボタンは右上に置く」 | 「この業務は操作速度を優先。金銭操作と削除は例外として確認を挟む」 |
| その画面だけに効く | すべての画面に効く |
| 書かれていない場面で空白が残る | 原則から演繹して空白を埋められる |

CLAUDE.md へ追記するときは、常に右の形（判断基準）に直せないかを先に考える。

## 2. 条文の抽象度5層（L1〜L5）

| 層 | 内容 | 例 | 扱い |
|---|---|---|---|
| L1 価値観（前文） | 案件が何を重く見るか | 「ユーザー入力を信用しない」「データの汚れより業務停止を重く見る」 | 単体では解釈がぶれる基盤。少数に留める |
| **L2 裁定基準** | **衝突したときの優先順位と例外条件**（AIに考えさせる層・主戦場） | 「操作速度と誤操作防止が衝突したら速度を優先。ただし金銭操作と削除は確認を挟む」 | **L2だけが「書いていない場面」に効く。** 憲法の中心 |
| L3 不変条件・禁止事項 | 解釈の余地なし（AIに考えさせない層） | 「物理削除は書かない」「金額に浮動小数点型を使わない」 | 作りすぎ・危険の防止はここで機能する |
| L4 規約・パターン指定 | ツール・書き方の統一 | 「dayjsに統一」「Result型でエラーを返す」 | **仮住まい。** 本来は lint・型・CIで強制すべき（/dev-standards「書いた規約より強制される規約」）。機械化できたら条文から削除する |
| L5 個別仕様 | 特定画面・特定機能の指定 | 「この画面の確定ボタンは右上」 | **憲法に入れない。** チケット・設計書（正本docs）に書く |

### 境目判定（唯一の基準）

> **半年後の別の機能でも、そのまま使えるか。**

使える＝L3以上として CLAUDE.md へ。使えない＝L5としてチケット・設計書へ。

### L2条文・L3条文の書き方テンプレート

```
L2: 【衝突条件】操作速度と誤操作防止 【優先】速度 【例外】金銭操作と削除は確認を挟む
L3: 【禁止】物理削除は書かない 【理由】監査追跡・復旧対応 【代替】論理削除で標準化
```

## 3. 憲法は「失敗から育つ文書」（還流ルール）

書き切ってから始めるのではなく、外れた解釈から条文を育てる。入力は解釈の宣言（assumption-management.md §6）の「根拠なし」項目と、実際に外れた解釈。

1. **一度きりの誤りは条文化しない**（チケットのコメントに留める。単発対応の積み上げはL5の肥大化になる）
2. **同じ種類の誤りが二度目に出たら条文化する**
3. 条文は「その機能だけ」の言い方ではなく、**案件のどの機能でも使える言い方に一般化してから**追加する（境目判定を通す）
4. **1回の追加は一行に限定**する（まとめて何行も足さない — 効かない条文の量産防止）
5. **条文の変更・追加は人間の承認必須**（CLAUDE.md は共有・コミット対象＝PRレビュー。生成物の都合で判断基準そのものが書き換わると憲法が汚染される — ai-security-baseline #11 と同じ統制線）

## 4. 肥大化の防止

- L4が増えるほど読む量が増え、L2の効きが薄まる。**lint・型・CIに落とせたL4は条文から削除する**（/llm-friendly-check の週次機械診断で検出）
- L5の混入（個別仕様）を見つけたらチケット・設計書へ移す
- 条文が効いているかは還流で判定する: 参照されない条文・同じ誤りを防げていない条文は書き直し候補

## 5. 人間の関門は2箇所（成果物全量から、基準の掌握へ）

AIの生成量が増えるほど「人が成果物を全部見る」は成立しない。人間が必ず握るのは次の2つで、これは省略・委譲できない:

1. **憲法の条文変更**（本標準 §3-5。判断基準の正本を握る）
2. **テストケース一覧の確定**（/test-planning「テストケース一覧の先出しと人間確定」。合格基準の正本を握る）

不可逆な操作（データ削除・外部公開・金銭移動・顧客提出）の人間承認は従来どおり別枠で維持する（enterprise-controls §D・各ゲート）。

## 6. 既存統制との関係（この標準が変えないもの）

- **仮定運用は変わらない**: 台帳のQ-IDに命中した未確定は従来どおり（仮定なしなら停止。assumption-management.md §4）。本標準が加えるのは、台帳未満の微細な空白を「条文からの演繹＋解釈の宣言」で埋める層（同 §6）
- **QCD基準・工程ゲート・生成/検証分離（Q-11）は変わらない**: 憲法は判断の演繹元であり、合否判定の代替ではない
- CLAUDE.md 生成時（/project-init フェーズ4）に、ヒアリング結果から初期のL2条文を数本起こして始める（ゼロ本で開始しない — 最初の演繹元がないと解釈の宣言が全件「根拠なし」になる）
